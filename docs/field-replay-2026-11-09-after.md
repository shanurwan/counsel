The notes are the ones the 9 Nov run wrote, with the duplicate check. On 10 Nov the code that settles duplicate claims was fixed and run over those recorded notes: a claim the check did not confirm, or one on an issue outside the candidate list, now reads "Related: #n", and an issue whose body has no words of its own (a lone screenshot) gets no duplicate. The model was not asked again. Read the same way, the notes from [before the check](field-replay-2026-11-09-before.md) named a duplicate on 84 issues, and maintainers confirmed 1.

## What it found

- **386 issues replayed**; maintainers had acted on 338 (a reply, a label or closing it).
- **Duplicates named:** **1 of 6** (lower bound 3%) confirmed by maintainers.
- **Duplicates caught:** **1 of 2** (lower bound 10%) of the issues maintainers closed as duplicates had one named in the note.
- **Missing information:** where a maintainer asked the reporter for more, the note had already said something was missing on **20 of 27** (lower bound 55%).

Lower bounds are Wilson, 95%: with this few issues, the bound is the honest number. A duplicate counts when GitHub records it as closed or marked as one. "Asked for more" is read from maintainers' comments and labels with a pattern, so read the table rather than trusting the counts alone.

## How the replay avoids hindsight

- The agent sees the title, body and author, not the labels, which maintainers mostly added later.
- Duplicate candidates are only issues opened before it and still open at that moment, from the 90 days before the window, ranked by the live agent's own similarity code.
- The prompt, the model and the code check on issue numbers are the live agent's.
